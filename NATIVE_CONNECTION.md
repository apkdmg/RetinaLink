# Direct connection and local Host approval

RetinaLink 0.7.0 retains the one-time signed Viewer installation and explicit two-screen approval introduced in 0.6.0, and adds automatic interface-scoped Ethernet discovery and selection. Host and Viewer are ordinary user apps. Standard setup never enables Remote Login, asks for an OS account password, edits `authorized_keys`, changes FileVault or alters automatic login/locking. Network selection observes existing macOS addresses without changing company network configuration. The optional privileged dedicated-account management flow remains a separate, explicit SSH administrator operation.

## First installation

Install Host on the main Mac and Viewer on the iMac using their respective DMGs. Host also offers **Save Viewer Installer…** to export its bundled notarized Viewer ZIP for copying once. Open the installed Viewer, then use **Add Display** on Host. Discovery finds unpaired Viewers; a manual iMac address works when multicast discovery is unavailable but direct traffic is allowed. Both apps show the same eight-digit number. The owner must compare it and approve on each Mac. Viewer startup is installed only in the signed-in user's session and starts after graphical login. FileVault's restart limitation is shown before approval. No claim is made that login agents can run before FileVault unlock.

Once paired, Viewer connects to Host directly over authenticated TLS using a random 128-bit credential stored in both login Keychains. It discovers the Host by its saved public Host ID and caches an address only after authentication. Discovery and cached addresses are hints, not trust. Host ID, stream credentials and binding survive compatible signed upgrades. A wrong discovery advertisement cannot supply the saved TLS key. Networks that isolate clients can still prevent direct communication; no router or SSH setting is silently changed to bypass that policy.

## Automatic Ethernet and multihoming

With a supported USB Ethernet adapter and an ordinary cable between the Macs, normal automatic macOS settings provide link-local communication without entering IP addresses. IPv6 link-local does not require a DHCP server; macOS can also fall back to IPv4 link-local. RetinaLink observes these addresses and discovers the paired Host on each available interface. It does not create static addresses, enable IPv6, change DHCP, alter routes/DNS/gateways/service order, enable Internet Sharing or modify company/VPN policies. See [DIRECT_ETHERNET.md](DIRECT_ETHERNET.md) for the cable arrangement and managed-network limitations.

`DirectLinkDiscovery` uses Bonjour TXT metadata and concrete `NWInterface` results. Each candidate keeps a typed service endpoint scoped to that interface, and `NWParameters.requiredInterface` constrains the connection. Network.framework retains the IPv6 link-local scope and resolves the service port. Scoped endpoints are never flattened into a hostname for connection, and interface indexes/scopes are not persisted across adapter removal or restart. The legacy stored address validator remains strict; scoped IPv6 syntax is not added to fields also used by legacy SSH management.

Live investigation on the Big Sur 11.7.8 receiver found a compatibility difference in `NWTXTRecord`: `NWBrowser` supplied a valid `hostID` through `record.dictionary`, but both its string subscript and `getEntry(for:)` returned nil. Filtering with those accessors discarded every scoped route even though legacy `NetService` discovery worked. `DirectLinkTXT` now extracts the identity from the compatibility dictionary, matches TXT keys case-insensitively, and requires a single bounded valid UUID value. Ambiguous duplicate keys and malformed identities are rejected; extraction does not authenticate a peer. Synthetic dictionary/wire-format tests cover this path, with live app results recorded separately in `VALIDATION.md`.

The preference policy ranks Ethernet with link-local addresses only ahead of configured Ethernet, then Wi-Fi. This is a route preference, not proof of physical topology: a company Ethernet port can also have link-local addresses, and a switch can carry them. Diagnostic labels describe the authenticated connection's interface and addressing rather than claiming a physically direct cable. Discovery metadata, address classification and public Host IDs remain untrusted hints; the saved TLS credential is still required.

While a stream works, a newly preferred Ethernet route receives a separate, rate-limited TLS probe. Failed authentication, a stale candidate or a mismatched required interface leaves the current stream alone. After successful TLS and interface verification, Viewer cancels the probe without sending a Viewer greeting and uses normal reconnection on the preferred route. Host allows bounded provisional connections alongside a stream; a transport-only probe cannot claim or stop that stream. Handover resets frame state and can briefly interrupt the picture. Failure recovery keeps the binding, applies per-route cooldowns and rotates attempts fairly so repeated preferred-route failures cannot permanently starve a fallback.

Live handover investigation also found that Host's brief Bonjour withdrawal/republication when the old stream closed could erase the selected Ethernet candidate. Viewer then reconnected on Wi-Fi before rediscovery, causing another Ethernet probe and a repeated switching cycle. Viewer now retains the already authenticated Ethernet intent for 15 seconds on a monotonic clock while waiting for the scoped candidate to return. The intent is ephemeral and cannot be created by an advertisement alone. If the route remains unavailable when the window expires, it clears the intent and resumes normal fallback; a genuine failed connection still receives its normal cooldown. This describes the recovery implementation, not a claim that the subsequent signed build or physical cable recovery has passed runtime validation.

If adapter support, manual network settings, disabled protocols or company multicast/client-isolation rules prevent discovery or traffic, RetinaLink waits or tries another available route. It does not change those settings to make a connection work. FileVault and startup/login behavior are unaffected.

## First-pairing authentication

`NativePairing.swift` uses CryptoKit X25519, SHA-256/HKDF and AES-GCM. Host and Viewer first commit to their ephemeral public keys, random 256-bit nonces and bounded identity metadata, then reveal them. Both sides verify the commitments. The canonical role-ordered transcript binds identities, nonces and public keys. Domain-separated derivations provide the displayed authentication string and independent Host→Viewer / Viewer→Host encryption keys. Comparing the string on both screens authenticates the exchange; simply clicking approval without comparing does not provide that guarantee.

All approval and enrollment messages are encrypted and transcript-authenticated. Strictly increasing counters reject replay and direction keys reject reflected messages. The owner approves through local UI methods; there is no network command to simulate a local approval. Enrollment is withheld until **both** local approvals have arrived. Viewer refuses to replace an existing pairing through this service. After committing, its setup listener closes. A lost final acknowledgment retains Host's saved half so an already committed Viewer can still reconnect. Version 0.6.1 also records a separate non-secret pending-setup marker before saving the first Host binding. If Viewer persistence is interrupted, retry requires the same Viewer identity and fresh local approval on both screens, then reuses the approved credential. Successful enrollment or an authenticated direct connection clears that marker; completed pairings cannot be replaced through this recovery path. Temporary Local Network permission waiting keeps the connection available until the setup deadline.

The service accepts one setup session at a time, caps attempts at six per five minutes, expires each session after two minutes and closes unpaired discoverability after ten minutes. It validates lengths before receiving bodies (16 KiB/message), bounds message counts and validates UUIDs, roles, names, usernames, commitments and keys. It accepts no shell commands, OS passwords, arbitrary file paths or software uploads. Diagnostics exclude keys, stream credentials and setup payloads. This protocol has implementation tests, not an independent cryptographic audit.

## Existing-pair migration

No re-enrollment is necessary. Viewer 0.6.0 reads its current binding/credential and discovers Host's new `hostID` TXT record. After authenticated direct TLS, Host persists a separate native-connection preference and closes the old app-owned SSH display master. It does not rotate credentials, rewrite the binding, delete restricted SSH keys, change FileVault or disable Remote Login. A one-time cleanup control operation can close an existing SSH socket; it does not initiate a new SSH login. Later native launches do not need an SSH server. Version 0.6.2 enables TCP keepalive probes after ten idle seconds (three probes, three seconds apart) so a half-open idle stream can be detected without requiring a screen change. Viewer then uses its normal reconnection path. These are transport liveness probes, not additional captured frames. Apple documents these options in [NWProtocolTCP.Options](https://developer.apple.com/documentation/network/nwprotocoltcp/options). The explicit legacy transport option remains for development/compatibility testing, not normal new setup.

Host sends Viewer update controls and explicit Forget Display requests through the authenticated app connection. Public signed updates use the GitHub feeds; from 0.8.3, relay-capable Viewers can receive their update through Host. See [Automatic updates](AUTOMATIC_UPDATES.md) and [VALIDATION.md](VALIDATION.md) for the current hosting, startup and hardware-test boundaries.

### One saved iMac across logins (0.8.4)

The 0.8.4 saved-display flow separates **one Host display profile** from each Viewer's private login Keychain. New Viewer versions derive their setup/discovery ID from a domain-separated hash of the iMac's IOPlatformUUID. The raw hardware UUID is not transmitted. Identity and discovery are public correlation hints: no ID, computer name, address or remote request grants trust. A new login receives the existing random TLS credential only after the user compares the committed verification number and approves locally on BOTH Macs.

Host's **Reconnect Display** retains its display name, enrollment date, credential and Dedicated Mode management metadata. Earlier approved Viewers therefore still authenticate without repeating setup. The approved Viewer saves a login-specific binding and optional startup agent. The saved hardware identity helps Host suggest reconnection; a conflicting known physical identity is rejected. Legacy Viewers remain compatible with the unchanged setup transcript and receive no claim of hardware identity. Manual-address approval can work without a discovery hint. Pending enrollment stores only non-secret target metadata and reuses the existing credential; retry still requires the same committed Viewer identity AND login. No shared plaintext trust file, root helper, account creation, SSH permission, automatic-login change or encryption change is needed.

Only the console login's production Viewer may start setup or initiate a display connection. Session resignation closes setup and streaming; session activation restarts normal discovery and reconnection. Unpaired standby remains discoverable without a ten-minute trip back to the menu. Handshakes remain bounded at 120 seconds and new attempts are rate-limited.

**Remove Display** and Viewer's **Reset Connection** revoke local trust only after checked Keychain deletion. They preserve FileVault, login and network settings; they do not claim to erase another login's Keychain. Removing the Host key revokes all old Viewer copies, even if those copies remain offline. Connected removal can also remove the current Viewer's pairing and startup. A Viewer reset returns it to local approval without deleting Host's saved display. Dedicated Mode's automatic-login target is never retargeted by reconnecting from another login.

## Tests and boundaries

`--native-pairing-test` and the native self-tests exercise committed identity checks, equal authentication strings, AES-GCM tampering, replay/reflection rejection, real TCP setup, one-sided approval refusal and a single commit after both approvals. They never write production trust.

`Tools/test_native_pairing.py` deploys the signed Viewer through an owner-authenticated SSH control socket and runs the actual approval controllers on both Macs in explicitly isolated UUID test domains. A separate test Keychain service is mandatory, and startup-agent installation is suppressed. It invokes the same local button actions through a launch-only local test seam, tests cancellation and one-sided approval before a successful fresh enrollment, injects an interrupted first Viewer enrollment and verifies retry retains the original approved credential, compares only disposable credential fingerprints, and verifies production Viewer binding/FileVault/public SSH keys are unchanged. Its interface exports render only the app's own view hierarchy; no UI capture helper is used.

Existing-pair direct streaming must be validated separately with both real installed apps, their unchanged bindings and normal startup agents, while the old app-owned display SSH master is absent. SSH may remain enabled solely for independent test deployment/log collection. That is evidence of no app-owned SSH tunnel, not a test that disables the system's Remote Login service or reboots the iMac. Native 5K dimensions and software presentation counters are not proof of stable physical 60 fps.

The 0.7.0 policy tests cover link-local/configured-address classification, interface ranking, typed IPv6 and Bonjour scope, unchanged legacy address validation, TLS-preserving interface constraints, bounded attempts and fair fallback recovery. A signed Viewer's explicit `--direct-link-probe` uses its saved credential silently, sends no application greeting or frames, and reports sanitized connection/interface metadata. Its time and attempt limits prevent an unattended diagnostic from running indefinitely. It does not export credentials or update trust.

Scoped authenticated traffic on the existing Ethernet LAN does not demonstrate that the company switch was bypassed. The UGREEN CM888 and direct cable are not connected for this release's testing: physical cable insertion/removal, a link with no DHCP server and recovery after actual unplug/replug remain pending. Tests use independent SSH diagnostics with the UI capture helper off; they must compare network configuration, pairing and FileVault before and after. See [DIRECT_ETHERNET.md](DIRECT_ETHERNET.md) and `VALIDATION.md` for the reported results and limits.
